# 使用教程

先完成[部署](DEPLOYMENT.md)，再按本页使用。中控面板管理的是你的业务 Worker；安装面板不会自动部署 CMliu、Joey、ECH。

## 1. 分清四种东西

| 名称 | 用在什么地方 | 从哪里来 |
| --- | --- | --- |
| 面板地址 | 浏览器打开管理页面 | Wrangler 上传后给出的 HTTPS 地址或自己的域名 |
| `ACCESS_CODE` | 面板登录框 | 安装时设置的 Secret |
| Cloudflare Account ID | 添加业务账号 | 对应账号的控制台或 Wrangler `whoami` |
| Cloudflare API Token / Global API Key | 面板操作该业务账号 | Cloudflare 的 API 凭据页面 |

登录口令不能替代 API Token。账号别名只用于识别，例如“备用账号”，不是实际账号 ID。

## 2. 登录并确认运行模式

1. 用 HTTPS 打开面板。
2. 输入 `ACCESS_CODE`。
3. 页面出现项目区、账号区和工具入口后再开始配置。

如果不知道运行模式，在浏览器控制台执行：

```javascript
fetch('/api/reliability/recovery').then(r => r.json()).then(console.log)
```

- `mode: "authority"`：SQLite DO 权威版，本页的持久任务和配置冲突说明适用。
- `mode: "legacy"`：KV 兼容版，按请求结果和工作台日志判断操作；不使用 DO 任务目录及面板兼容日期保存。
- 401：重新登录。
- 503：交给部署管理员检查，不能把已有 authority 实例改成 legacy 来“修好”。

会话 Cookie 通过 HTTPS 发送。页面写请求自动携带 CSRF 校验信息；不要复制 Cookie 到别人电脑或关闭校验。

## 3. 添加第一个业务账号

1. 打开账号工具，选择添加账号。
2. 填一个容易识别的别名。
3. 填真实 Account ID。
4. 选择认证方式，填写对应凭据。
5. 已经有业务 Worker 时，分别填写其 CMliu / Joey / ECH 名称；没有时先留空，后续用批量部署创建。
6. 保存后使用凭据验证或刷新 Worker 清单，确认 API 权限正常。

推荐使用能限定账号和权限的 API Token。权限取决于要执行的操作：

| 操作 | 需要的主要能力 |
| --- | --- |
| 查询 / 上传 / 删除 Worker | 对目标账号的 Workers Scripts 读写 |
| 创建、绑定或写入 KV | Workers KV Storage 读写 |
| 查询区域 / 绑定域名与路由 | 对相应 Zone 的读取、Workers Routes 等实际需要的权限 |
| 查询用量 | 对应分析数据的读取权限 |

具体权限名称以 Cloudflare 控制台为准。先选账号再选权限，不要给不需要管理的所有账号授权。

只有 Global API Key 时，选择 Key 方式，并同时填写账号邮箱。切换认证方式时应保存新选择，不要把 API Token 填进 Global Key 框。

**成功标志**：保存后账号出现在列表，凭据验证或 Worker 查询成功。出现掩码 `***` 表示后端隐藏了凭据，不表示凭据丢失。

## 4. 配置项目变量

1. 选择 CMliu、Joey 或 ECH 项目。
2. 编辑变量名和值。
3. 应保密的变量勾选 Secret。
4. 保存变量，再执行部署。

| 项目 | 常见关键项 | 存储特点 |
| --- | --- | --- |
| CMliu | `UUID`、`PROXYIP` 等 | KV 绑定名通常为 `KV`，优选节点键为 `ADD.txt` |
| Joey | `u` 等 | KV 绑定名通常为 `C`，节点配置键为 `c` |
| ECH | `PROXYIP` 等 | 该模板不使用项目 KV，不参与 UUID 熔断轮换 |

实际变量含义以对应上游项目说明为准。不要把中控面板的 `CONFIG_KV` 名称当成业务模板 KV 绑定名。

权威模式的草稿和已保存配置不同。保存遇到 409 时，先重读服务器配置、比较并合并；不要反复点击覆盖。兼容模式建议同一时间只用一个页面编辑。

## 5. 第一次创建业务 Worker

先对**一个账号、一个新 Worker 名称**操作：

1. 在批量部署入口选项目。
2. 只选刚添加的那个业务账号。
3. 填一个未使用的 Worker 名称，例如 `demo-cmliu`。
4. 按模板需要选择变量、KV 和域名设置。
5. 阅读部署预览，核对账号 ID、名称、上游版本和资源操作。
6. 确认部署。

权威模式收到 `202 / accepted` 后，打开任务列表等终态；兼容模式查看本次返回结果和工作台日志，并到 Cloudflare 核对资源。

**成功标志**：目标 Worker 已存在，任务或操作结果显示成功，页面提供的业务地址可访问。网络或代理功能还需要按上游项目方式单独验证，不能仅凭 Worker 存在判断全部功能正常。

创建成功后确认账号的项目 Worker 列表中有这个名称。普通“更新”处理的是已关联的目标，不会凭空猜出要管理哪些 Worker。

## 6. 更新、指定版本和自定义源码

- **跟随上游**：先检查更新，阅读变更，再部署最新版本。
- **指定版本**：在版本历史中选择目标提交，可收藏并起别名，然后确认部署范围。
- **自定义源码**：选择本地代码内容并预览。公开任务 JSON 有独立大小限制，不等于上游源码的读取上限。
- **只更新部分账号**：核对目标列表。局部成功不代表所有账号都已到同一版本。

权威模式会在接纳时冻结源码、变量、目标和兼容日期。任务排队后再修改配置，不会改变已接纳的任务。

### 修改兼容日期（仅权威模式）

三个项目各有独立设置，默认 CMliu / ECH 为 `2024-04-05`，Joey 为 `2026-01-20`。修改后保存，只影响之后接纳的任务。

允许日期从 `2021-11-01` 到当天；选择上游实际支持的日期，不因为日期新就直接改成今天。

## 7. 看懂任务结果（仅权威模式）

| 状态 | 意思 | 下一步 |
| --- | --- | --- |
| `queued` | 已接纳，排队中 | 等待或查看前序任务 |
| `running` | 正在执行 | 查看步骤状态 |
| `succeeded` | 已验证完成 | 查看目标地址与结果 |
| `failed` | 失败 | 查看原因，核对远端状态 |
| `partial_failed` | 一部分已完成，另一部分失败 | 保留任务 ID，只处理明确失败的范围 |
| `cancelled` / `partial_cancelled` | 已取消全部或尚未执行的部分 | 已完成的外部操作不会自动撤回 |
| `needs_review` / 步骤 `unknown` | 无法确认外部操作结果 | 请管理员核对；不要用新请求键绕过屏障 |

收起任务面板只是停止本页轮询，后台任务继续。刷新、断网、按钮恢复也不表示取消。取消是一项明确请求；已经上传或删除的内容不会因取消自动回滚。

工作台用于即时日志和诊断，服务器任务记录才是持久依据。保存 task ID / request ID，分享日志前先脱敏。

## 8. 自动化与通知

需要两层都启用：

1. 部署配置里有 Cloudflare Cron 触发器。
2. 面板中开启自动检查，并保存间隔、参与模板、用量阈值和通知设置。

用量阈值触发的 UUID 轮换会影响客户端配置或订阅，先理解影响再启用。ECH 没有 UUID 字段，只参与适用的版本更新。

权威模式支持约定格式的企业微信、钉钉和飞书机器人 Webhook。地址可能包含密钥，按敏感配置保管。业务任务结果和通知送达结果分别显示：业务成功不等于通知一定发出。

先以较长间隔运行少量账号，观察用量和任务结果，再调整频率。

## 9. 资源管理、优选节点和 1101 修复

- **移除账号配置**：只是从面板中移除，不等于删除远端 Cloudflare 账号或 Worker。
- **删除 Worker**：会修改远端资源。确认名称和是否处理关联 KV；共享 KV 的保留情况以返回结果为准。
- **修改账号子域名**：可能影响该账号多个 workers.dev 地址，先确认影响范围。
- **优选节点**：选项目、目标账号和节点范围，再写入对应项目配置。Joey 的变量方式还涉及变量保存与重新部署。
- **1101 修复**：包含备份、重建、绑定/域名恢复等步骤，部分账号还可能轮换子域名。先读并确认完整目标清单。权威模式会保留受保护账号的账号级子域名；这不表示其业务 Worker 不会变化。

1101 修复是有副作用的运维操作。出现未知结果时保存原任务信息，交由管理员处理，不能不停点击再创建删除/重建任务。

## 10. 备份与恢复

| 方式 | 能恢复什么 | 谁来操作 |
| --- | --- | --- |
| 账号导入 / 导出 | 账号及相关凭据信息 | 面板用户；文件应私下保管 |
| 兼容模式配置备份 | 旧 KV 配置范围 | 兼容模式用户，按界面预览核对 |
| 权威归档与恢复 | 协议约定的配置、凭据、runtime、任务相关材料 | 有独立维护密钥的管理员 |
| Git 代码仓库 | 源码和公开文档 | 开发者；不包含线上数据库与密钥 |

权威模式的完整备份/恢复通过维护工具执行。浏览器里的旧 KV 备份不能当成当前 DO 数据快照，也不能拿它直接覆盖活动数据。

## 11. 排错顺序

先看“哪一步、哪种模式、什么状态”，再处理：

| 错误 | 处理 |
| --- | --- |
| 401 | 重新登录同一 HTTPS 地址 |
| 403 / CSRF / Origin | 检查地址协议和会话；刷新页面，不去掉校验 |
| 400 / INVALID | 核对输入、完整目标、保护资源和大小限制 |
| 409 | 读取当前配置或原任务；区分版本冲突、重复意图、状态屏障 |
| 428 | 页面协议旧，重新加载当前版本 |
| 503 / NOT_READY | 管理员检查运行模式、绑定、密钥、初始化或维护状态 |
| 任务很久没变化 | 查看是否有 unknown 前序、未送达回执或维护状态；不要自动重发写操作 |

记录面板版本、request ID、task ID、时间和脱敏错误。部署配置的问题看[部署教程](DEPLOYMENT.md)，DO 维护问题看[运维指南](OPERATIONS.md)。
